## 구현

- `plugin/chzzk.py:source_paths()`는 `SourcePath`에 CDN, HLS/LL-HLS, 현재/과거, 대입 후보 여부를 보존한다. 한국 → 알 수 없는 제공 CDN → Akamai, 같은 CDN에서는 LL-HLS → HLS 순이다. `_get_live()`는 첫 유효 경로의 화질을 선택하며 마지막 예비 결과로 덮어쓰지 않는다.
- 알려진 두 한국 HTTPS 현재 호스트(`nvelop-livecloud.pstatic.net`, `livecloud.pstatic.net`)만 Akamai로 대입한다. 경로·서명·쿼리는 그대로 유지한다. 이미 제공된 같은 Akamai 후보는 중복 추가하지 않는다. 알 수 없는 호스트나 과거 경로를 무작위로 바꾸지 않으며 폐기된 `nlive-streaming.navercdn.com` 치환은 복구하지 않았다.
- `hls_continuity.py:ChzzkM3U8Parser`는 설치된 Streamlink 8.6.2의 parser를 확장해 PART/PART-INF/SERVER-CONTROL과 정확한 DISCONTINUITY-SEQUENCE를 읽는다. PDT가 한 번만 주어진 연속 구간은 이전 길이로 이어 계산한다. 설치된 라이브러리 파일은 수정하지 않았다.
- 공개된 미완료 묶음의 부분 조각은 bounded request pool에서 미리 받는다. 미리 받는 future와 완료 묶음 다운로드가 같은 요청을 공유하며 한 segment thread에서도 교착 없이 동작한다. PRELOAD-HINT를 확정 조각으로 받지 않는다. 부분 캐시는 64개, init/key 캐시는 기존 16/8개다.
- 완료 묶음은 실제 조각 수·길이·MAP/KEY·URI 및 데이터 중복·GAP·컨테이너를 확인하고 전체 조각으로 한 번만 출력한다. 누락·잘림·길이 불일치·중복·미지원/암호화 부분 형식은 부분 바이트를 버리고 전체 조각을 받는다. 기존 전체 AES-128 복호화와 완료 조각 커서를 유지한다.
- Blocking reload는 서버의 CAN-BLOCK-RELOAD와 실제 다음 MSN/PART를 사용한다. 원래 서명 쿼리를 재인코딩하지 않으며 target duration에 따른 읽기 예산을 준다. 정상 대기는 미디어 hedge/복구 이벤트를 생성하지 않는다.
- 예비 준비는 별도 조회 작업이다. 대입 Akamai는 동일 화질·시각·길이·불연속 구간을 찾고 init 비교 및 실제 미디어 다운로드까지 성공한 뒤 ready를 알린다. 이 작업은 primary를 변경하지 않는다. 실패한 준비도 이후 복구에서 재확인할 수 있다.
- 한국 현재/과거 후보를 먼저 조회하고 첫 조회가 2초를 넘거나 소진되면 Akamai도 조회한다. 미디어 실패뿐 아니라 목록 중간 누락에도 적용한다. 모든 작업은 기존 90초 복구 기한을 공유하고 조각당 최대 두 미디어 요청, 전체 요청 슬롯 제한을 유지한다. 과거 후보는 목록 끝 기준 최근 최대 1시간이다.
- 기존 방송 ID·화질·날짜·길이·init·불연속 경계 검증에 절대 불연속 번호를 추가했다. 예비 목록의 네트워크 잠금은 주 목록과 분리했다. 지속적인 manifest 403이 재귀적으로 discovery를 부르는 경로도 제거했다.
- `recording_continuity.py`, `chzzk_record.py`의 additive `source` 이벤트는 CDN·수신 방식·선택/준비/부재/실패 상태만 허용하며 추가 URL 필드를 제거한다. 기존 이벤트/설정/resume 형식은 유지한다. `i18n.py`와 README 다섯 언어, Knowledge와 계획을 갱신했다.

## 검증

- 최종 전체 검사: **71개 통과, 실패·오류·건너뜀 0**, 약 20.6초. 기존 47개에 24개를 추가했다. 로컬 HTTP 서버와 실제 Streamlink reader/writer, FFmpeg 및 녹화 관리자 파일 전환을 실행한다. 테스트 서버 실행에 필요한 로컬 소켓 권한은 승인된 실행으로 확인했다.
- 새 사례: 가변 PART 수, 누락/잘림/중복 URI·본문, 불완전 길이/GAP, 일반 HLS 및 AES-128 전체 대체, 공개된 부분 미리 받기, blocking reload, 한 thread의 future 공유/요청 상한, 한국 이력 우선, 느린 이력 중 Akamai 복구, Akamai 단독, 예비 준비 실패/성공/init 불일치, 대입 URL의 서명 보존/호스트 제한/중복 제거, 1시간·불연속 번호 경계와 URL 없는 이벤트/5개 언어.
- 실제 FFmpeg 부분 수신 재현: 17개 fMP4 fragment를 4/5/3/5개의 가변 묶음으로 제공하고 한 부분 조각을 잘랐다. 해당 묶음만 전체 조각으로 한 번 대체했다. 출력은 원본 바이트와 같고 영상 **1,000프레임**을 보존했다. 음성 프레임 수와 영상·음성 PTS 간격 검사도 통과했다. 기존 1,000프레임 이력 복구 및 실제 파일 전환 검사도 유지했다.
- 공개 녹두로 방송의 한국 CDN 짧은 수신: 첫 실행은 PART 26회/blocking reload 25회, 26,544,801바이트, 영상 1,560/음성 1,219프레임, FFmpeg 0·오류 출력 0, 영상 최대 PTS 간격 0.017초/음성 0.021334초, gap/복구 이벤트 0이었다. 당시 API는 한국 주소만 제공했다. JTBC 공개 API에서도 한국 주소만 확인했다.
- 사용자 추가 지시 후 실제 주소 대입: 한국 API 현재 HLS/LL-HLS의 호스트만 Akamai로 바꾼 master는 둘 다 HTTP 200, 5개 variant, 동일 시각/길이/불연속 구간 및 init SHA-256 일치, 실제 약 2MB media 검증에 성공했다. 반환되는 주소와 서명은 기록하지 않았다.
- 새 예비 준비를 포함한 한국 실방송 약 25초: PART 29회/blocking reload 26회, 영상 1,560/음성 1,218프레임. 한국 LL-HLS selected와 Akamai LL-HLS ready 이벤트를 관찰했다. FFmpeg 0·오류 출력 0, 영상/음성 최대 간격 0.017/0.021334초, gap 0.
- 실제 실방송 형식의 검사 실행에만 한 시각의 모든 한국 후보 다운로드 실패를 주입했다. 한국 실패 호출 4회 후 **한국 LL-HLS → Akamai LL-HLS → 한국 LL-HLS** 출력을 관찰했다. 영상 1,560/음성 1,219프레임, FFmpeg 0·오류 출력 0, 영상/음성 최대 간격 0.017/0.021334초, gap 0. VPN/시스템 네트워크나 사용자의 녹화 프로세스를 변경한 것은 아니다. 자연 CDN 장애 재현은 아니다.
- 실방송 수신은 HTTP/1.1이었다. HTTP/2 라이브러리나 추가 의존성을 설치하지 않았다. 이후 pending PART future 공유 개선은 한 thread 회귀 검사와 최종 전체 검사로 확인했다.
- 수정 Python 6개 파일 문법 컴파일과 `git diff --check`를 확인했다. 중간 미디어/진단 스크립트는 `/tmp`에만 있다. HAR 원문·서명 URL·쿠키·개인 API 응답은 저장소에 넣지 않았다.

## 남은 범위

- 현재 사용자 접속은 한국이다. 해외 VPN에서 이 최종 버전의 장시간 녹화, 자연 CDN 장애, Windows/macOS 및 실제 회원 전용 방송은 미검증이다. 원본 5시간 로그의 모든 실패가 해결됐다고 단정하지 않는다.
- Akamai 호스트 대입은 이번 공개 방송에서 확인한 동작이며 모든 방송/서명의 영구 계약이 아니다. 실패하거나 구간·초기화가 다르면 사용하지 않고 기존 복구 기한/공백 경로를 따른다.
- 모든 암호화 부분 형식을 지원하지 않는다. 전체 HLS 대체는 유지하며, 원래 미지원 암호화/암묵 byte range 한계는 그대로다. 강제 종료 후 커서 영구 복원은 범위 밖이다.
