## 로그에서 확인한 문제

- 원본 위치: `/home/munsy0227/다운로드/log.log`. 로그 전체나 인증정보를 저장소에 복사하지 않았다.
- 약 5시간, 80,744행. 복구 이벤트 138회 중 완료 127회, 복구 실패·파일 전환 11회. 경고의 확인 가능한 누락은 2초씩 총 22초였다.
- FFmpeg 입력 `start`와 직전 최종 `out_time` 비교로 전환 공백 약 68.1초가 추정됐다. 실제 원본 영상 디코딩으로 확정한 손실량은 아니다.
- 원래 `fetch()`/`between()`은 현재 후보 목록의 시작 시각만으로 required media를 만료됐다고 판정할 수 있었다. `fail()`은 다음 위치를 버리고 `boundary(None, reason)`으로 최신 위치에서 재시작했다. 상세 HTTP/구조 실패 원인이 번역 로그에 없었다.

## 실제 변경

- `hls_continuity.py`: known URI의 재시도를 sliding playlist 범위만으로 조기에 끝내지 않는다. 구간 재시도는 목록을 다시 받는다. 실패 복구 중 API 갱신은 최소 5초 간격이며 401/403의 기존 즉시 갱신을 유지한다. 복구 기한·순서·중복 방지·같은 방송/화질·init 검증·요청 수 제한·중지 처리는 유지한다.
- 다음 위치가 있는 gap은 가장 이른 다음 조각 시각을 파일 전환에 넘긴다. 다운로드 실패 조각은 그 조각의 끝, 목록 중간 누락은 이미 알고 있는 다음 조각의 시작을 사용한다. 방송 종료나 위치를 알 수 없는 경우에는 임의 위치를 만들지 않는다.
- `recording_continuity.py`/`plugin/chzzk.py`: `after_gap`은 JSON boolean으로 검증한다. 확인된 gap 뒤에는 제공되는 가장 이른 후속 위치로 이어갈 수 있고, 요구한 시각도 사라졌으면 추가 공백을 경고한다. 일반 discontinuity/init 변경은 정확한 resume을 요구한다. 과거 시작 옵션은 재연결 때 반복하지 않는다.
- URL 없는 진단 이벤트는 단계·역할·분류·HTTP 상태·조각 번호·시각만 전달한다. 중복 기록 캐시는 128개로 제한한다. 녹화 관리자는 검증한 필드만 DEBUG 로그로 출력해 추가 JSON 속성의 원문 예외/URL/쿠키가 전달되지 않게 한다.
- `chzzk_record.py`/`i18n.py`: gap의 원인 안내와 진단 문구를 5개 언어로 추가하고, 복구 시작 안내를 누락 또는 지연으로 정확히 표현했다.
- 기존 `tests/test_hls_continuity.py`에 회귀 사례를 확장했다. 5개 README, 기존 구현 계획 및 Knowledge를 현재 동작에 맞췄다.

## 검증

- 기존 Streamlink 8.6.2/Python 3.12 환경을 그대로 사용했다. 추가 의존성 설치는 하지 않았다.
- 수정 전 기존 전체 검사: 37개 통과, 실패/건너뜀 0.
- 수정 후 전체 검사: 47개 통과, 실패/오류/건너뜀 0. 실제 로컬 HTTP 서버, Streamlink writer, FFmpeg 녹화 관리자 경로를 실행했다.
- 회귀 재현 4개를 원래 코드에도 실행했다. sliding window의 known URL 재시도, 늦게 제공되는 이력 목록, 사라진 gap resume 이후 가장 이른 위치, 실제 파일 전환이 모두 기존 코드에서 실패하고 수정 코드에서 통과했다.
- 실제 FFmpeg 전환 재현: 원래 코드의 영상 프레임 `[250, 250]`에 비해 수정 코드는 `[250, 500]`을 보존했다. 총 1,000프레임 중 접근 불가능한 한 조각 250프레임만 제외한 750프레임이다. 복구 불가능한 조각을 복원했다는 뜻은 아니다. failed media 응답 사례도 `[250, 500]`; 일반 discontinuity는 `[500, 500]`이었다.
- 기존 1,000프레임 및 음성 PTS 연속성 복구, 일부 복구 후 공백, 초기화 불일치 거부, token/API 갱신, 예비 조회 지연, 종료·중지, 요청 수 상한 검사도 포함한다.
- 진단 필드 타입/열거값, 추가 예외/URL/쿠키 필드 제외, 중복·캐시 제한, 5개 언어 원인 문자열을 검사했다.
- 공개 JTBC 방송의 짧은 실제 녹화: wall-clock 종료 타이머 75초, 저장 미디어 약 80초, 84,280,588바이트. Streamlink 130(중지 신호), FFmpeg 0, ffprobe 디코딩 0. 영상 4,800프레임·최대 PTS 간격 0.016667초, 음성 3,750프레임·최대 PTS 간격 0.021334초. FFmpeg 및 디코딩 오류 출력 0. 이 짧은 실행에서 실제 복구/장애 이벤트는 관찰하지 않았다.
- Python 컴파일과 `git diff --check`를 확인했다. 진단 중 만든 대용량 영상/임시 로그는 프로젝트 밖의 작업 폴더에만 있다.
