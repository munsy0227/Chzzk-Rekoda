## 코드에서 확인한 남은 문제와 설정 안내

- `hls_continuity.py:ChzzkContinuityReader.read()`는 마지막 전달 후 `RECOVERY_TIMEOUT + 5`(현재 95초) 동안 무진행이면 `writer.fail(previous, None, "output_stalled")`를 호출한다.
- `ChzzkContinuityWriter.fail()`은 다음 조각이 None일 때 `resume_from=None`을 보내며 마지막 정상 조각 끝은 gap 안내에만 사용한다. `recording_continuity.py:RecordingContinuity.accept()`는 이 boundary에서 resume을 None으로 설정한다. 다음 실행에는 `--chzzk-resume`이 전달되지 않아 현재 제공 위치에서 시작한다. 경고의 `to Unknown` 및 약 92~94초의 파일 전환 공백과 일치하는 코드 경로다.
- 후속 개선의 핵심은 다음 조각을 모르는 무진행 전환에서도 마지막 정상 출력 위치를 보존하고, 재시작 전에 동일 방송·화질의 현재/과거 경로에서 후속 조각을 찾는 것이다. 복구할 미디어가 실제로 제공되는지는 이번 로그만으로 확인할 수 없다. 이번 요청은 분석이므로 이 개선을 구현하지 않았다.
- 정기 분할을 끄려면 전역 `recording_split_minutes=0`과 채널별 override를 확인한다. `recording_options.py:effective_split()`상 채널 0은 전역과 무관하게 분할을 끄고 null/누락은 전역 상속이다. GUI는 녹화 설정 → 기본 녹화 → 파일 분할 간격의 사용 안 함 및 채널 설정을 사용한다. 변경은 새 녹화 작업에 적용한다.
- GitHub 장시간 테스트는 workflow가 설정 파일을 다시 생성하므로 로컬 개인 설정 변경으로 해결되지 않는다. 테스트 전체 녹화물을 보존하려면 정기 분할 설정과 오래된 파일 삭제 정책을 함께 검토해야 한다. 5분 분할을 꺼도 현재 수신 장애 전환은 새 파일을 만들기 때문에 방송 전체 단일 파일을 보장하지 않는다.

## 검증과 미검증

- 로그 전체를 읽어 이벤트·오류·파일명·입력 start·최종 out_time을 집계했다. FFmpeg 파일 열기 61개는 모두 서로 다른 경로였다.
- 현재 workflow/script, FFmpeg 출력 구성, 분할 override, 수신 reader/writer와 resume 전달을 대조했다. `git diff --check`가 통과했고 추적하지 않는 새 작업 기록의 whitespace도 별도로 확인했다. 로그 집계와 공백 합계는 별도 재계산으로 일치함을 확인했다.
- 녹화 영상이 제공되지 않아 디코딩·프레임/음성 연속성을 검증하지 않았다. 새 실방송/5시간 재실행, 실제 CDN 장애 원인, 최종 출력 디렉터리, 삭제된 영상의 복원 가능성은 미검증이다.
