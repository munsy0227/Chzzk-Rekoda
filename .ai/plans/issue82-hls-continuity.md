# 이슈 #82: 다중 CDN 수신과 누락 조각 복구

작성·구현 확인: 2026-10-10. 최초 분석 제안 이후 사용자가 구현을 승인했다. 아래는 승인된 범위와 실제 구현이며, 서비스 관찰·검증 결과는 [작업 기록](../worklogs/2026-10-10-issue82-hls-analysis.md)에 있다. 원격 게시와 디스크 부족 정책 변경은 범위에 포함하지 않는다.

## 승인된 동작

- 기본 시작은 Streamlink의 현재 방송 위치다. 기존 무조건적인 `--hls-live-restart`를 제거했다.
- API가 실제 제공한 일반 HLS와 긴 목록의 CDN 주소만 사용한다. 호스트를 임의로 교체하지 않고 P2P/그리드 프로그램을 실행하지 않는다.
- 주 요청이 2초 지연되면 예비 요청을 시작하며, 주 요청 실패에는 즉시 예비 경로를 조회한다. 조각당 동시 미디어 요청은 최대 두 개다. 완전히 받고 검증한 결과 중 먼저 성공한 것을 한 번만 순서대로 출력한다.
- 마지막으로 출력한 위치 이후의 누락을 현재·긴 목록에서 복구한다. 시각이 없으면 같은 목록과 조각 번호만 사용한다. 방송 ID·화질·시작 시각·길이·discontinuity 및 초기화 데이터가 일치하지 않는 대체 조각은 사용하지 않는다.
- API 후보는 30초마다 갱신하며 토큰 오류에는 즉시 갱신을 시도한다. 예비 목록/API 조회의 지연·일시 실패가 이미 성공한 주 요청을 지연하거나 취소하지 않도록 한다.
- 필요한 다음 조각을 90초 동안 받지 못하거나 보관 범위 밖임이 확인되면 공백을 경고하고 최신 위치부터 새 파일을 만든다. 이후 조각을 같은 파일에 이어 써서 공백을 숨기지 않는다. 방송 종료와 사용자 중지는 이 복구 대기보다 우선한다.
- 초기화 데이터 변경/discontinuity에는 다음 조각 시각을 녹화 관리자에게 전달한다. 관리자는 출력 파이프와 stderr를 비우고 FFmpeg·기존 파일을 정리한 뒤 그 위치에서 새 파일을 시작한다.

## 설정과 타임머신 가용성

- 전체 설정 `record_previous_hour` 기본값은 `false`다. 채널의 같은 키는 `null`이면 상속하고 JSON `true`/`false`이면 채널 선택을 우선한다. 문자열 `"false"` 등은 활성화 값으로 취급하지 않는다.
- GUI의 기본 녹화 체크박스와 채널의 전체 설정 따름/사용/사용 안 함 선택, CLI 녹화·화질 6번과 채널 관리 4번에 연결했다. 다음 방송 시작에 최신 설정을 다시 읽으며 진행 중인 녹화는 변경하지 않는다.
- 켜면 최신 완료 조각을 기준으로 실제 제공되는 최근 최대 1시간에서 가장 오래된 접근 가능한 조각부터 시작한다. 처음 조각을 내려받아 검증하고 404/410이면 제한된 탐색으로 살아 있는 범위를 찾는다. 과거 목록/조각이 없거나 접근을 확인하지 못하면 기본 현재 위치로 시작한다. 부족한 분량은 실제 초 단위로 안내한다.
- 과거 시작은 채널 녹화 세션의 각 방송에서 한 번만 적용한다. 자동 재연결/파일 전환/분할에서 다시 과거를 저장하지 않는다. 새 방송 ID에는 다시 적용할 수 있다.
- **타임머신 버튼 또는 `timeMachineActive`만으로 접근 가능성을 판정하지 않는다.** 사용자 예시 두 채널은 UI 플래그가 false였으나 실제 제공 범위가 각각 약 1시간/10분이었다. 권한 있는 API가 제공한 주소, dated playlist, 실제 미디어 접근과 초기화 검증을 사용한다. 이 관찰을 모든 채널의 영구 보관 정책으로 일반화하지 않는다.
- 시작/복구 시작·완료/공백/전환은 `CHZZK_REKODA_EVENT ` 표식과 버전 1 JSON stderr 이벤트를 사용한다. 방송 ID·화질·시각·진단 분량만 전달하고 URL/쿠키/토큰을 포함하지 않는다. 관리자에서 이벤트를 검증하고 5개 언어 로그로 표시한다.

## 실제 코드 연결

- `plugin/chzzk.py:source_paths()`는 `live-detail` HLS media와 그 `encodingTrack.p2pPath`에 포함된 `cdn_url`을 추출한다. 인코딩된 값은 API가 광고한 HTTP CDN 주소이며 P2P 프로그램 실행이 아니다. 기존 회원 전용/쿠키 검사를 유지한다.
- `hls_continuity.py:ContinuitySource`는 화질별 manifest pool, 주기/API 갱신, 조각 위치 대응, 누락 구간 탐색을 담당한다. 역할별 CDN origin 두 개와 origin별 경로 두 개로 후보 수를 제한한다.
- `ChzzkContinuityWorker/Writer/Reader`는 고정 Streamlink 8.6.2 HLS 계층을 확장한다. 미디어 다운로드뿐 아니라 init map도 검증하며, 실패/빈 결과를 조용히 건너뛰는 기본 writer 경로를 대체한다. 다운로드 스레드·20개 출력 큐·요청/조회 작업 수를 제한하고 중지 이벤트와 읽기 제한을 사용한다.
- 검증은 HTTP Content-Length/byte range 완전성, TS 패킷 경계, ISO-BMFF 최상위 box 경계와 필수 moov/moof/mdat, 대체 후보 init SHA-256 일치다. 각 조각을 FFmpeg로 디코딩하는 검증은 런타임에서 수행하지 않는다. AES-128 전체 조각 복호화 경로는 유지한다.
- `recording_continuity.py:RecordingContinuity`는 방송별 한 번의 과거 시작과 다음 파일의 resume 시각을 관리한다. `chzzk_record.py:record_stream()/read_log_stream()`이 기존 프로세스·파일 정리와 연결한다.
- `recording_options.py`, `config_store.py`, `settings.py`, `gui/settings_dialog.py`, `i18n.py`와 5개 README를 함께 변경했다. Qt 의존성은 GUI 계층에만 있다.

## 검증과 한계

- `tests/test_hls_continuity.py`의 제어 가능한 HTTP 서버로 지연/실패/응답 중단/느린 응답 본문/토큰·API 실패/누락/복구/전환/중지/설정을 검사한다. 실제 Streamlink writer와 FFmpeg 녹화 관리 경로를 사용한다.
- 이전 실방송 fMP4 재현 입력의 복구 결과는 원본 바이트와 같고 1,000프레임 및 오디오 PTS 연속성으로 확인했다. FFmpeg 반환 코드나 표시 재생시간만으로 성공을 판정하지 않는다.
- discontinuity 전환은 실제 파일 두 개에 각 500프레임, 복구 불가능한 누락은 경고와 최신 위치의 새 파일 두 개에 각 250프레임을 확인했다. 미완성 `.part`는 남지 않았고 두 번째 실행에 과거 시작을 반복하지 않았다.
- Linux에서 현재·과거 위치의 짧은 공개 실방송 녹화, Qt offscreen 5개 언어 설정, Python 컴파일 및 whitespace 검사를 수행했다. 정확한 실행 명령/집계는 작업 기록을 참고한다.
- 약 1시간 보관이나 복수 CDN은 보장된 서비스 계약이 아니다. 후보가 하나면 해당 경로만 사용한다. 원본 신고 파일 전체·YouTube 처리, 장시간 녹화, Windows/macOS, 실제 계정/회원 전용, 실방송에 강제로 넣은 CDN 장애는 미검증이다.
- 프로세스 강제 종료 뒤 이전 커서의 영구 복원은 이번 범위가 아니다. 과거 시작 중복은 세션 내에서 막으며, 확인 가능한 공백에서 파일 전환한다. implicit-offset HLS byte range와 AES-128 외 암호화는 명시적으로 거부한다.
